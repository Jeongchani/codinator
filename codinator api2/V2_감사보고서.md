**C-1. 수동 블러(Manual Blur) Fallback 완전 미구현**

증상: AI 서버가 다운되거나 실패하면 이미지 업로드 자체가 502/504 오류로 실패. 사용자가 게시글을 올릴 수 없음.

근거 파일: `apps/api/src/modules/uploads/uploads.service.ts`

왜 문제인지:
- V2 확정 기능서에서 "자동 블러 실패 시 수동 블러 가능" 정책 명시
- 현재 `UploadsService.savePostImage()`에서 `await this.aiService.blurFace(file)` 호출이 실패하면 `BadGatewayException` 또는 `GatewayTimeoutException`을 throw하여 업로드 전체가 실패
- `blurMethod: 'MANUAL'`로 설정되는 코드 경로가 존재하지 않음
- `aiBlurStatus: 'DONE'`을 항상 하드코딩 반환 (FAILED 케이스 없음)

재현 조건: AI 서버(AI_SERVER_BASE_URL)가 응답 불가 상태에서 이미지 업로드 시도

권장 해결:
```typescript
// uploads.service.ts 수정
let processed: FaceBlurResult;
let blurMethod: 'AUTO' | 'NONE' | 'MANUAL' = 'NONE';
let aiBlurStatus: 'DONE' | 'FAILED' | 'NONE' = 'NONE';

try {
  processed = await this.aiService.blurFace(file);
  blurMethod = processed.blurred ? 'AUTO' : 'NONE';
  aiBlurStatus = 'DONE';
  // 처리된 이미지 저장
} catch (e) {
  this.logger.warn('AI blur failed, using original image as fallback');
  // MANUAL fallback: 원본 이미지를 processed로 복사
  blurMethod = 'NONE'; // 또는 'MANUAL' (관리자 수동 처리 대기)
  aiBlurStatus = 'FAILED';
  // originalFullPath를 processedFullPath로 복사
}
```

수정 우선순위: **Critical** — AI 서버 장애 시 업로드 기능 전체 마비

영향 범위: `uploads/uploads.service.ts`, `PostImage.aiBlurStatus`, `PostImage.blurMethod`

**C-2. 북마크 localStorage 의존 (API 미연결)**

증상: RankingDetail에서 북마크 추가/삭제가 localStorage에만 저장됨. 브라우저 새로고침, 다른 기기, 탭 전환 시 초기화.

근거 파일: `apps/web/src/pages/ranking/RankingDetail.tsx` L35, L150-153

왜 문제인지:
- localStorage의 'codinator_bookmarks' 키에만 저장
- `POST /posts/:postId/bookmarks`, `DELETE /posts/:postId/bookmarks` API가 존재하지만 미연결
- 서버 DB에 데이터가 저장되지 않으므로 `GET /users/me/bookmarks` 응답이 항상 비어있음
- 북마크가 실질적으로 동작하지 않는 더미 기능 상태

재현 조건: 랭킹 상세에서 북마크 → 브라우저 새로고침 또는 시크릿 모드로 접속

권장 해결:
- RankingDetail.tsx의 북마크 핸들러에서 `fetcher('/posts/${postId}/bookmarks', { method: 'POST' })` 호출로 교체
- DELETE도 동일하게 API 연결
- localStorage 코드 제거

수정 우선순위: **Critical** — 북마크 기능 자체가 비동작 상태

영향 범위: `apps/web/src/pages/ranking/RankingDetail.tsx`

**C-3. UserReport PENDING 중복 — Race Condition 가능**

증상: 사용자 신고 API를 동시에 2번 호출하면 PENDING 신고 2건이 생성될 수 있음.

근거 파일:
- `apps/api/prisma/schema.prisma` (UserReport 모델 — `@@unique` 없음)
- `apps/api/src/modules/reports/reports.service.ts` (서비스 레벨 `findFirst` 체크만)

왜 문제인지:
- Report(게시글 신고)는 `@@unique([reporterId, postId])`로 DB 레벨에서 중복 차단
- UserReport(사용자 신고)는 unique 제약이 없음
- 서비스 레벨에서 `findFirst({ status: PENDING })` 체크는 동시 요청 시 두 요청 모두 "없음"을 확인 후 각각 INSERT
- 동일 사용자가 동일 대상에게 PENDING 신고를 여러 건 생성 가능

재현 조건: `POST /users/:userId/reports`를 동시에 2번 호출

권장 해결:
```prisma
model UserReport {
  ...
  // 아래 partial unique index 추가 (PostgreSQL 지원)
  @@unique([reporterId, reportedUserId, status]) // OR
  // 서비스 레벨에서 트랜잭션 + upsert 사용
}
```
또는 Prisma 트랜잭션 + serializable isolation level 사용

수정 우선순위: **Critical** — 데이터 정합성 깨짐, 신고 어뷰징 가능

영향 범위: `schema.prisma`, `reports/reports.service.ts`, migration 필요

**H-1. Admin 엔드포인트 URL이 Notion 명세와 불일치**

증상: Notion API 명세서에는 `PATCH /admin/post-reports/:reportId`로 정의되어 있으나 실제 구현은 `PATCH /admin/reports/:id`.

근거 파일:
- Notion 명세: `/admin/post-reports/:reportId`
- 실제: `apps/api/src/modules/admin/admin.controller.ts` — `@Patch('reports/:id')`

왜 문제인지:
- 프론트엔드 개발 또는 외부 연동 시 잘못된 URL로 구현될 수 있음
- Notion 명세 상태가 "시작 전"으로 되어 있어 명세와 구현 모두 혼선 발생
- 명세서가 Source of Truth인데 구현이 다름

## 별도 섹션 — 중요 정책 5가지 심층 검증

### 1. 자동 블러 실패 시 수동 블러 Fallback 구현 여부

**판정: ❌ 미구현**

`UploadsService.savePostImage()` 코드:
```typescript
const processed = await this.aiService.blurFace(file);
// ↑ 실패 시 BadGatewayException throw → 업로드 실패
```

- `blurMethod: 'MANUAL'`로 설정되는 코드 경로 없음
- AI 실패 시 수동 블러 대기 상태로 저장하는 로직 없음
- `AiBlurStatus.FAILED`, `AiBlurStatus.PENDING` 상태가 실제로 저장되지 않음
- **Severity: Critical** — AI 서버 불안정 시 게시글 업로드 기능 전면 중단

### 2. user_reports PENDING 중복 제한의 안전성

**판정: ⚠️ 서비스 레벨만 있음, DB 레벨 없음**

- `Report` (게시글 신고): `@@unique([reporterId, postId])` — DB 레벨 완전 보호 ✅
- `UserReport` (사용자 신고): unique 제약 없음. 서비스 레벨 `findFirst` 체크만 ❌
- 동시 요청 시 race condition으로 PENDING 중복 생성 가능
- `@@index([reporterId, reportedUserId, status])` 인덱스는 있으나 unique 보장 안 함

**권장**: PostgreSQL의 partial unique index 또는 `@@unique([reporterId, reportedUserId])` 추가 + 서비스에서 PENDING 체크 유지

### 3. 피드 공개 범위 정책 분리 여부

**판정: ✅ 분리되어 있음 (단, CLOSED 이슈 있음)**

| 피드 종류 | 조건 | 구현 |
|----------|------|------|
| 내 피드 | DELETED 제외 전체 (OPEN/ENDED/CLOSED 포함) | ✅ 일치 |
| 타인 피드 | ACTIVE + ENDED + publishedAt + READY 랭킹 | ⚠️ CLOSED 누락 |
| 평가존 | OPEN + 본인 게시글 제외 | ✅ 일치 |
| 검색 | ACTIVE + !OPEN | ⚠️ publishedAt/READY 조건 미확정 |

### 4. 북마크의 OPEN/ENDED/CLOSED 동작

**판정: ✅ OPEN 포함 전체 허용 (DELETED만 제외)**

```typescript
// bookmarks.service.ts
const post = await this.prisma.post.findFirst({
  where: { id: postId, status: { not: PostStatus.DELETED }, deletedAt: null },
```

- ACTIVE(OPEN 포함), HIDDEN 모두 북마크 가능
- DELETED만 차단
- V2 정책 "북마크는 OPEN 게시글도 가능" 충족 ✅
- 단, 내 북마크 목록에서는 HIDDEN 게시글도 표시됨 (`postStatus: 'HIDDEN'` 반환)

### 5. 피드백 태그 3개 정책의 일관성

**판정: ⚠️ 백엔드와 프론트 불일치**

| 레이어 | 제한 | 구현 |
|--------|------|------|
| Request 검증 (백엔드) | 3개 | `if (unique.length > 3)` — ✅ |
| DB 저장 | 3개 이하 | createMany로 저장 — ✅ |
| 응답 | 저장된 tagIds 반환 | `selectedTagIds` — ✅ |
| 프론트 UI | **1개** | "최대 1개까지만 선택" — ❌ |
| 프론트 API 전송 | **1개** | `tagIds: [selectedKeywordId]` 고정 — ❌ |

백엔드는 3개를 지원하지만 프론트는 1개만 허용. 정책 재확인 필요.

## 마지막 — 최종 정리

### 1. 지금 당장 배포하면 위험한 것

**① AI 블러 실패 = 업로드 기능 전체 중단 (C-1)**
AI 서버가 잠깐이라도 불안정하면 모든 사용자의 게시글 업로드가 502/504로 실패. 서비스 핵심 기능 마비.

**② 북마크 데이터 손실 (C-2)**
사용자가 북마크를 해도 서버에 저장되지 않음. 브라우저 캐시 삭제, 기기 변경 시 모두 초기화. 사용자 신뢰 문제.

**③ 사용자 신고 중복 데이터 (C-3)**
동시 신고 요청 시 DB에 중복 PENDING 신고 생성. 관리자 처리 혼선 및 데이터 정합성 깨짐.

### 2. 정책 문서와 가장 크게 어긋나는 것

**① 수동 블러 fallback 완전 미구현 (C-1)**
V2 확정 기능서에 "자동 블러 실패 시 수동 블러 가능" 명시. 현재 AI 실패 시 수동 처리 경로 자체가 없음.

**② MyFeedEdit 더미 데이터 (H-3)**
내 피드 수정은 V2 핵심 기능인데 UI만 있고 실제 저장이 전혀 안 됨. 사용자 입장에서 기능이 없는 것과 동일.

**③ 피드백 태그 1개 vs 3개 불일치 (H-4)**
V2 기능서 "태그 최대 3개" → 백엔드 3개 허용 → 프론트 1개 제한. 프론트/백엔드/정책 3자 불일치.

### 3. 수정하면 완성도가 가장 많이 올라가는 것

**① 프론트엔드 미구현 페이지 일괄 추가 (H-7)**
마이페이지, 검색, 북마크 목록, 신고 UI 등을 추가하면 백엔드가 이미 모두 완성된 상태이므로 완성도가 크게 상승. 개발 공수 대비 완성도 향상 효과 최대.

**② MyFeedEdit API 연결 + 북마크 API 연결 (H-3, C-2)**
각각 1개 파일 수정으로 중요 기능 2개를 실동작 상태로 만들 수 있음.

**③ 수동 블러 fallback 구현 (C-1)**
단일 파일 수정(`uploads.service.ts`)으로 AI 장애 내성을 갖추어 실제 운영 가능 상태 달성.
